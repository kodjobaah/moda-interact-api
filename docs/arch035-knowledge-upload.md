# ARCH-035-API-017: Woo Merchant Knowledge file lifecycle

The WooCommerce PHP plugin uses the authenticated Moda merchant endpoints, not direct PostgreSQL or R2 credentials. `POST /v1/merchant/merchant-knowledge/upload-intents` returns a ten-minute R2 PUT URL for a single immutable CSV/XLSX object. The plugin alone may consume that URL; never render it into JavaScript/HTML or store it in WordPress. All upload endpoints require the existing installation ID and bearer credential. Request and response details are in `openapi/merchant-knowledge-v1.yaml`.

## Upload sequence

1. PHP computes the exact file size and lowercase SHA-256 of the uploaded bytes, chooses one supported source-pair from the catalogue, and creates an intent with a stable client-generated UUID `idempotencyKey`. Retrying the same intent after a network timeout uses the same UUID and *identical metadata*.
2. PHP checks the signed PUT URL: `https`, no userinfo, the expected configured R2 account origin, no redirected target, no private/IP/loopback destination, no unexpected port. Fail closed when the URL cannot be proven to match the approved origin. Apply a bounded network timeout and request size; never forward the PHP installation bearer or other Moda credentials to R2.
3. PUT bytes directly to the signed URL with exactly the returned `Content-Type`, `If-None-Match: *` and `x-amz-meta-sha256` header values. Do not follow 3xx redirects. The R2 object must be immutable during the intent lifetime.
4. `POST /v1/merchant/merchant-knowledge/upload-finalize` with `assetId`, `purposeKey`, `name`, `languageTag`, `sizeBytes`, `sha256`, `contentType`, and optional *owned* `sourceId` for replacement. The API checks HEAD metadata and streams GET bytes to recompute SHA-256 and size before transactional source/revision changes. A repeated finalize returns the same revision, not a duplicate. R2 unavailability fails closed.
5. The persisted revision is initially `PENDING`; the existing Background reconciliation handles ingestion when entitlement and merchant activation permit it. Returning an accepted revision is **not** a claim that it was queued or ingested. Metadata updates and reprocess use the authenticated source endpoints.

The path is generated only on Moda's server: `merchant-knowledge/<deployment-env>/woocommerce/<validated-shop-id>/<asset-uuid>/source.csv|xlsx`. The Shop ID comes from the verified installation, never from Woo HTTP input. Shopify's existing `merchant-knowledge/<env>/<myshopify-domain>/...` keys are unchanged. Background's uploaded-asset acquisition selects `objectKey` from `MerchantKnowledgeUploadedAsset` and feeds it into its R2 `getObject`, with no Shopify-domain validator; it already supports this new namespace.

## Deployment configuration (API service only)

The upload routes lazily load `MERCHANT_KNOWLEDGE_R2_ENDPOINT`, `MERCHANT_KNOWLEDGE_R2_BUCKET`, `MERCHANT_KNOWLEDGE_R2_ACCESS_KEY_ID`, `MERCHANT_KNOWLEDGE_R2_SECRET_ACCESS_KEY`, and `MERCHANT_KNOWLEDGE_MAX_UPLOAD_BYTES`. Endpoint must be a Cloudflare account S3 endpoint (`https://<32 hexadecimal digits>.r2.cloudflarestorage.com`), with no custom port or URL credentials. Max upload size is a positive byte count bounded to 25 MiB. Secrets are never exposed to WooCommerce or log metadata. Configure these variables in the service deployment using secret storage; any necessary Render Blueprint updates belong to `moda_gateway`, **not** API-017. The existing read-only API continues without R2 configured; upload routes return 503.

Validate with `npm run test:arch035-knowledge-upload:postgres` (disposable Docker PostgreSQL with deployed migrations), `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` and `git diff --check`. Integration fixtures include actual CSV and XLSX bodies; the unit suite checks request bounds, signer metadata/host and byte integrity.
